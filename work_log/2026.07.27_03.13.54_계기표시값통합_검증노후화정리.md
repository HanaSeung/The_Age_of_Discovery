## 2. 막대를 점으로 — 세 점이 크기·테두리를 공유한다

> 바람을 하늘색 원으로, 해류를 적당한 색의 원으로 바꾸려고 한다. 이해한 것을 설명만 하라.
> 그리고 해류는 어떤 색이 좋을지 추천하라.

직사각형 막대를 원으로 바꾸면 드러나는 문제 셋을 먼저 짚었다.

1. **해류 색을 반드시 바꿔야 한다.** 해류가 `#c0392b` 로 침로 점과 **완전히 같은 색**이었다.
   지금까지는 "막대 vs 점" 이라는 모양 차이로 구분됐지만, 둘 다 원이 되면
   같은 원 위에 똑같이 생긴 붉은 점이 두 개 돈다.
2. **겹쳤을 때 읽히는 장치가 사라진다.** 막대는 굵기 차(6.0 vs 2.8)가 마지막 단서였다.
3. **테두리 규칙이 둘로 갈려 있다.** 막대는 어두운 테두리, 침로 점은 밝은 테두리를 썼다.

해류 색으로 네 안(자수정 / 호박 / 은백 / 남색)을 배경 조건과 함께 비교하고
**자수정색 `#8e6bb5`** 를 추천했다. 바다 청록(`#8bb0a8`)의 보색에 가까워 밝은 쪽에서
또렷하고, 어두운 띠 위에서도 명도가 충분하기 때문이다.

### 아이삭의 결정

> 해류색은 '자수정색'으로 하고, 침로, 바람, 해류원의 테두리 색은 침로색과 같이 한다.
> 그리고 원의 크기도 현재 침로 크기로 통일한다.

크기·테두리가 같아지면 완전히 겹칠 때 아래 점이 사라진다는 점을 알리고,
그리는 차례(바람 → 해류 → 침로, 침로가 맨 위)를 유일한 구분 수단으로 삼기로 했다.

### 구현

`bar(ang, halfW, fill)` 를 `dot(ang, fill)` 하나로 바꾸고 침로 점도 같은 함수를 쓰게 했다.
셋이 한 함수를 통과하므로 크기·테두리가 어긋날 방법이 없다.

상수 `BAR_LEN`·`BAR_W`·`BAR_W2`·`BAR_EDGE` 넷을 걷어내고
`DOT_R`·`DOT_EDGE_W`·`DOT_EDGE`·`HEAD_C`·`WIND_C`·`CUR_C` 여섯으로 갈았다.
인라인 hex 를 전부 상수로 뽑아 색 조정이 한 곳에서 된다.

파수꾼 둘을 새로 넣었다 — 옛 막대 상수가 남거나 `strokeRect`/`fillRect` 가 되살아나면
잡힌다. §6 에는 "침로 점을 따로 그리지 않는다" 를 넣어, 나중에 침로만 손으로 다시 그려

## 5. 바깥 끝을 맞춘다 — 기준점의 뜻이 자리마다 다르다

> 바람과 해류를 좀더 원의 테두리쪽으로 붙여야 한다.

- 위·아래 글자는 기준점이 글자 상자의 **한가운데** → 실제 바깥 끝은 글자 높이의 절반만큼 더 나간다

그래서 넷의 기준점은 같은 원 위에 있었지만, 눈에 보이는 바깥 끝은
위아래 108px, 좌우 101~105px 로 좌우가 안쪽에 앉았다.

세 안(현행 / 좌우만 7px / 넷 모두 7px)을 점선 기준 원과 함께 미리보기했고,

## 7. 두 기계(C:/D:) 문제와 verify_helm 전면 개정

> 검증실패 다섯은 그대로 둬도 되는건가?

다섯을 실제로 돌려 원인을 확인했다.

| 파일 | 증상 |
|---|---|
| `verify_helm` | `ENOENT: 'D:\MyApp\...'` — 경로가 D 드라이브로 박힘 |
| `verify_sail` | `Cannot read properties of null` — 정규식 불일치 |
| `verify_sailable` | `ReferenceError: SHIP is not defined` |
| `verify_windsail` | `ReferenceError: SHIP is not defined` |
| `verify_zoom` | 유일하게 끝까지 돌며 42/4 보고 |

넷이 **아무것도 검사하지 못하는 상태**임을 알렸다. `verify_ui` 에서 겪은 것과 같은
문제이며, 이들이 맡은 영역이 조타·돛·항해 가능성이라 특히 위험하다고 판단했다.

> 현재 게임 작업은 작업 컴퓨터에 따라 c:와 d: 에서 하고 있다.
> '경로가 D 드라이브로 박혀 있다.'고 했는데, 이것과 관련이 있을까?

관련이 있었다. 전체를 훑어 현역 파일 중 문제가 되는 것은 `verify_helm.js` 하나뿐임을
확인했다(나머지는 `path.join(__dirname, ...)`, 걸린 셋은 은퇴 폴더).

**여기서 제가 한 추측이 틀렸다.** "D 기계에서는 통과했을 것" 이라고 말씀드렸으나,
경로를 고치자 13번째 줄의 정규식이 CRLF 를 못 맞춰 터졌다 — 즉 D 에서도 이미 실패하고
있었다. 다음 턴에서 정정하고 사과했다.

### 세 겹의 노후

경로를 고치자 `verify_helm.js` 가 오래전부터 세 겹으로 썩어 있었음이 드러났다.

1. **경로가 절대경로** — C 기계에서 통째로 터짐
2. **정규식이 CRLF 를 못 맞춤** — `<script>\n"use strict"` 의 `\n` 하나로는 `\r\n` 을 못 잡는다
3. **물리 상수를 베껴 둠** — `SPEED=235, ACC_UP=70…` 을 제 안에 적어 두었는데, 원본에서는
   `syncDerived()` 가 배 제원에서 매번 계산해 내는 파생값이다. 베낀 숫자가 어긋나도
   아무도 모르는 구조 — 시뮬레이션이 조용히 거짓말을 하게 된다

게다가 `chk()` 도 집계도 종료 코드 처리도 없는 **보고서** 였다. 세 갈래(응급처치 / 재작성 /
은퇴)를 제시했고 아이삭이 **재작성**을 택했다.

### 새 verify_helm.js

제원을 원본에서 뽑아 쓰고(`speedKn:8, sailMax:4, turnDeg:66, turnIdle:0.12, accUp:3.4, accDn:1.8`),
뽑는 자리가 사라지면 그 자체로 실패한다. 파생 공식도 원본과 대조하므로 계산 방식이 바뀌면
즉시 걸린다. `상수를 이 파일에 베껴 두지 않았다` 검사가 스스로를 읽어 재발을 막는다.

```
돛 0/4 → 0.0 kn    돛 4/4 → 8.0 kn = 제원 8 kn
정지→전속 3.4일 / 전속→정지 1.8일  (감속이 1.9배 빠르다)
정지 7.9°/일   돛2/4 37.0°/일   전속 66.0°/일 = 제원 66°/일
정지 선회가 제원의 0.120 배 = turnIdle 0.12
```

도중에 제가 새로 짠 검사 둘이 틀려 고쳤다. 선회 측정을 속력 0 에서 시작해 가속 구간이
섞이는 바람에 66° 가 56° 로 나왔다 — 각 단수의 정상 속력에서 출발하도록 바꿨다.

### 절대경로 파수꾼

두 기계를 오가는 작업 방식이 계속되므로 재발 방지를 넣었다. `verify_boot.js` 6절이
모든 `verify_*.js` 를 훑어 절대경로가 박힌 줄을 찾는다. 주석은 건너뛰고, 구분자 뒤에
낱말이 이어져야 경로로 본다 — 처음엔 `verify_ship.js` 의 정규식 리터럴 `!/rng\('c:/` 를
경로로 잘못 잡아 조건을 좁혔다.

```
verify_helm.js  통과 31, 실패 0
verify_boot.js  통과 (파수꾼 포함)
```

## 부록 C. 이번에 효과가 있었던 방법

**1. 미리보기를 여러 안으로 그려 놓고 고르게 한 것.**
이번 세션에서 네 번 썼고(안 A~D / 변형 1~3 / 바깥끝 vs 색점고정 / 붙이기 세 안),
그때마다 말로 설명하는 것보다 결정이 빨랐다. 특히 "값 3.1 과 12.3" 처럼 **같은 안을
서로 다른 입력으로** 그려 보인 것이 자릿수 문제를 한눈에 드러냈다.

**2. 여러 곳에서 하던 일을 한 함수로 모은 것.**
`dot()` · `lab()` · `tag()` · `side()`. 셋이 한 함수를 통과하면 크기·테두리·외곽선이
어긋날 방법이 없다. "따로 그리지 않는다" 를 검사로 지키면 나중에 누가 되돌려도 잡힌다.

**3. 상수를 뽑되, 뽑는 양까지 상수에서 나오게 한 것.**
`RING_R` 의 뜻을 바깥 끝으로 바꾸고 물러나는 양을 `GEO_F/2` · `GS_F/2` · `TAG_R` 로 둔 덕에,
글자 크기를 바꿔도 정렬이 저절로 유지된다. 값을 고정하는 것보다 **관계를 고정**하는 편이 낫다.

**4. 검사가 통과한다고 검사가 살아 있는 것은 아니다.**
`verify_ui` 는 39개 검사 중 하나도 돌지 않은 채 목록에 "실패 1" 로만 보였다.
`verify_helm` 은 상수를 베껴 두어 시뮬레이션이 거짓말을 할 준비가 되어 있었다.
**요약을 못 내는 파일은 의심해야 한다.**

**5. 파수꾼을 함께 넣은 것.**
옛 막대 상수 잔재 · 모서리 판 복귀 · 자리 상수 분리 · 절대경로. 문제를 고칠 때마다
"같은 문제가 다시 생기면 잡히는가" 를 한 줄 넣었다.

**6. 틀렸을 때 바로 정정한 것.**
"D 기계에서는 통과했을 것" 이라는 추측이 틀렸음을 다음 턴에서 확인하고 정정했다.
검사 둘도 제가 잘못 짜서 고쳤다. 추측은 표시하고, 확인되면 고친다.
