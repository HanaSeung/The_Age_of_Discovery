## 2. 문제 제기 — 보이는 바다를 지나지 못한다

> (스크린샷 첨부) 분명히 바다인데 배가 이 사이를 지나지 못한다. 정확한 원인과 해결책을
> 제시하되, 업계에서 통상적으로 사용하는 방법으로 제시하라.

밤바다에 두 육지 사이 물길이 넓게 열려 있는데 배가 그 사이를 통과하지 못하는 화면.

먼저 코드를 읽어 구조를 파악했다.

| 항목 | 값 |
|---|---|
| 월드 | `WORLD_W 8192 × WORLD_H 4096` (equirectangular) |
| 충돌 마스크 | `MASK_W 8192 × MASK_H 4096`, **1셀 = 1월드px = 4.892km** |
| 그리기 | `landPath` (Path2D, evenodd) — 벡터 |
| 막기 | `landMask` — `landPath` 를 캔버스에 그려 픽셀을 되읽은 이진 래스터 |
| 이동 | 도착점 한 점 검사 + 축 분리 슬라이드(x만 / y만) |
| 좌초 | `ship.speed=0; ship.sail=0; ship.grounded=true` |

`dt` 는 `loop()` 에서 0.05초로 잘리고 `TIMEK = P.hoursPerSec/24` (기본 2.0/24 = 0.0833)
이라, 기본 시계에서 한 걸음은 0.30 월드px. 관통이 날 만큼 크지는 않았다.

## 3. 진단 — 실측

임시 스크립트로 `land_data.js` 를 Node 에서 직접 디코드해 측정했다.

**해협이 마스크에서 살아남는가** (`_strait_probe.js`)

```
지브롤터   폴리곤 4.50px(22.0km) | 마스크 5.00px(24.5km)
보스포루스 폴리곤 0.14px(0.7km)  | 마스크 0.00px(0.0km)  ← 막힘
다르다넬스 폴리곤 0.50px(2.4km)  | 마스크 0.72px(3.5km)
도버       폴리곤 8.22px(40.2km) | 마스크 8.22px(40.2km)
```

**벡터와 마스크의 어긋남** (`_strait_probe2.js`)

```
해안 ±3px 표본 399,143점
  보이는 바다인데 못 지나감 (보이지 않는 벽) : 2.99%
  보이는 육지인데 지나감   (육지 관통)       : 2.96%

격자 양자화 오차 최대 = 0.71셀 = 3.46km
  배율   5배 → 화면에서   4px 어긋남
  배율  13배 → 화면에서   9px 어긋남
  배율  40배 → 화면에서  28px 어긋남
  배율 100배 → 화면에서  71px 어긋남
```

**결론**

그리는 것은 벡터 폴리곤이고 막는 것은 4.892km 격자다. 배율 13배까지는 어긋남이 화면 9px
라 눈에 띄지 않지만, `ZMAX` 를 100으로 열어 둔 지금은 화면 71px — 배 그림보다 큰
'보이지 않는 벽'이 된다. 스크린샷의 물길은 화면 약 135px 이고, 배율 100배면 1.35셀 = 6.6km
라 양쪽에서 3.46km 씩 먹혀 닫힌다.

**부수 원인 셋**

1. 축 분리 슬라이드는 계단·대각선 해안에서 두 축이 동시에 막히면 그 자리에서 완전 정지
2. 스윕 없는 점 검사 — 시계를 올리면 좁은 물길을 건너뛰고 반대편 육지에 착지 판정
3. 좌초 시 `sail=0` — 스칠 때마다 돛이 내려가 "영영 못 지나간다"는 체감을 키움

또한 `C` 키의 충돌 표시가 마스크가 아니라 `landPath` 를 붉게 덧칠하는 것이라
이 어긋남이 보이지 않았다. 진단이 어려웠던 이유다.

**제시한 해결책 4안**

| 안 | 내용 | 평가 |
|---|---|---|
| 1 | 벡터 충돌 — 선분을 격자에 색인, 스윕 원 vs 선분, 법선 슬라이드 | **권장.** 그리는 것과 막는 것이 같아짐 |
| 2 | SDF(부호거리장) — 거리를 구워 두고 쌍선형 보간 | 대안. 굽는 코드가 더 무거움 |
| 3 | 다중 해상도 마스크 — 배 주변만 고해상도로 재래스터화 | 손이 덜 가지만 계단은 남음 |
| 4 | 배율 상한 복구(ZMAX 13) | 근본 해결은 아니나 원 설계 의도 |

## 4. 결정

> 지도 배율은 100.00x 이다. 그리고 너의 추천안으로 하자.

배율 100 확인으로 원인이 확정됐다. 안 1 + 안 4 로 진행하기로 함.

설계와 색인 규모를 제시했다.

```
선분 60,527개, 총 해안선 길이 952,485km, 선분 평균 15.74km
CELL  4px | 격자 2048x1024 | 항목 135,001 | 칸당 평균 2.1 | 최대 17 | 8.5MB
CELL  8px | 격자 1024x512  | 항목  94,045 | 칸당 평균 3.6 | 최대 37 | 2.4MB  ← 채택
CELL 16px | 격자  512x256  | 항목  76,362 | 칸당 평균 7.0 | 최대 90 | 0.8MB
```

> 결정에 대해 쉽게 설명하라.

세 결정을 쉬운 말로 다시 설명했다.

1. **`HULL_KM`** — 배를 점으로 볼지 반지름 있는 원으로 볼지. 작으면 좁은 물길을 다 지나지만
   배 그림이 육지에 얹혀 보이고, 크면 넉넉히 피해 돌지만 좁은 해협이 막힌다
2. **좌초 시 돛** — 새 방식은 해안을 스치는 일이 잦아지므로, 스칠 때마다 돛이 내려가면
   불편하기만 하다. 사고의 맛은 나중에 선체 손상·수리로 살리는 편이 낫다
3. **배율 상한** — 벡터 충돌이 들어가면 100배에서도 벽이 사라지므로 급하지 않다.
   다만 100배에서 보이는 해안선은 실제 모양이 아니라 굵은 직선 근사다

> 1. 작게 하라.  2. 빼라.  3. 나는 게임을 100으로 하려고 한다.

`HULL_KM = 0.2` (반지름 200m, 지름 400m) 로 정했다. 이 지도 자료가 표현할 수 있는 가장
좁은 물길인 보스포루스(0.7km)까지 열린다.

반지름이 작아지면 고정 잔걸음은 걸음 수가 폭발하므로, **자유거리 전진**(sphere tracing)
으로 설계를 바꿨다. 먼바다는 한 번에 끝나고 해안에 닿았을 때만 잘게 움직인다.

## 5. 구현

**① 해안선 선분 추출** — `landPath` 디코드 루프에서 같은 자료로 `COASTSEG`
(Float32Array, 선분당 x0,y0,x1,y1) 를 함께 만든다. 고리를 닫는 변도 넣는다.

> 이름 충돌: 그리기 색 상수 `const COAST='#6b4a2a'` 가 이미 있어 `COASTSEG` 로 지었다.
> 같은 스코프에서 `let COAST` 와 `const COAST` 를 함께 선언하면 SyntaxError 가 난다.

**② 격자 색인** — CSR 구조. 2회 훑기(계수 → 누적합 → 채우기).

```js
const CGW = WORLD_W/COL_CELL, CGH = WORLD_H/COL_CELL;   // 1024 x 512
cellStart : Uint32Array(CGW*CGH+1)
cellItem  : Uint32Array(94,043)
```

**③ `nearestCoast(x,y,R,out)`** — 반경 안 최근접 해안까지의 거리와 바깥 법선.
경도 이음매는 칸 오프셋 `ox = (gx-wx)*COL_CELL` 로 보정한다(월드 폭의 배수가 된다).

**④ `moveWithCoast(x,y,dx,dy,out)`**

```
① 자유거리(= 최근접거리 - HULL_R)만큼 한 번에 전진 — 먼바다는 한 번에 끝
② 닿으면 안으로 파고드는 성분만 깎는다 (바다 쪽 성분은 살린다)
③ 남는 방향이 없으면 멈춘다 (좌초)
```

불변식은 **"배는 언제나 해안선에서 `HULL_R` 이상 떨어져 있다"**. 거리 0을 지날 일이
없으므로 육지 관통이 원리상 일어나지 않는다. 시계를 아무리 빨리 돌려도 같다.
안팎 판정(inside/outside)이 필요 없다는 것이 이 설계의 이점이다.

**⑤ 이동부 교체** — 극 차단은 해안을 따지기 전에 변위를 먼저 자른다.
좌초 시 `ship.speed=0` 만 하고 `sail` 은 건드리지 않는다.

**⑥ `C` 키 표시** — `landPath` 를 `lineWidth = HULL_R*2` 로 덧그어, 실제로 못 들어가는
띠를 눈으로 보이게 했다.

`landMask` 와 `isLand` 는 존치 — 해류 육지 마스킹, 폭풍 자리 고르기, 육지 발견이 계속 쓴다.

## 6. 검증과 그 과정에서 잡은 결함

`verify_coast.js` 를 새로 썼다. 원본에서 토막을 오려 vm 샌드박스에서 그대로 돌린다
(`Path2D` 와 `document` 는 껍데기, `land_data.js` 는 실제 자료).

**결함 ①** — `nearestCoast` 가 브루트포스와 최대 7.3px 어긋났다. 추적하니 어긋난
점이 전부 `y = 4096` (지도 맨 아래변, 남극) 이었다.

```js
if(gy0<0) gy0=0; if(gy1>CGH-1) gy1=CGH-1;   // 위만 잘랐다
```

`y=4096` 인 선분은 `gy0 = gy1 = 512` 인데 `gy1` 만 511로 잘려 `for(gy=512; gy<=511)`
가 되어 **한 번도 돌지 않았다.** 그 선분들이 색인에서 통째로 빠졌다.
양끝을 다 자르도록 고쳐 오차가 4.4e-16px 이 됐다. 색인과 조회 양쪽 모두 고침.

**결함 ②** — 사용자가 브라우저에서 확인하니 배가 해안에 걸리면 빠져나오지 못했다
(38.1°N 14.6°E, 시칠리아 북안). 접촉 처리가 **접선만** 보고 있었다.

```js
const dot = ux*HIT.tx + uy*HIT.ty;
if(Math.abs(dot) < 1e-6){ out.stop=true; break; }
```

배가 해안 쪽으로 가는지 바다 쪽으로 가는지를 구분하지 않아 증상이 둘로 나타났다.

1. 바다로 나가려 해도 접선 성분만 남으니 해안을 따라 미끄러지기만 한다 — 떠날 수 없다
2. 뱃머리를 바다로 **정확히** 돌리면 접선 성분이 0 이라 "정면으로 받음"으로 오판해
   완전히 멈춘다 — 빠져나오려는 가장 올바른 조작이 가장 확실히 막혔다

오목한 모서리가 이를 굳혔다. 한 선분을 따라 미끄러지면 다른 선분에 막히고,
바다로 돌리면 2번에 걸린다.

**고침** — `nearestCoast` 가 접선 대신 최근접점을 잡아 **바깥 법선**을 돌려준다
(선분 안쪽이면 수직, 끝점이면 방사 방향 — 둘 다 벗어나는 쪽이라 옳다).

```js
const dn = ux*HIT.nx + uy*HIT.ny;                          // 양수면 바다 쪽
let mx = ux, my = uy;
if(dn < 0){ mx = ux - HIT.nx*dn; my = uy - HIT.ny*dn; }    // 파고드는 만큼만 깎는다
```

**시험 설계에서 두 번 헛디딘 것** — 충돌이 아니라 시험이 틀렸던 경우가 둘 있었다.
기록해 둘 값어치가 있다.

- 해협 통과 시험을 *목표를 향해 탐욕적으로 조타*하게 짰더니 오목한 모서리에서 갇혀
  지브롤터·말라카가 실패했다. 항로 탐색은 충돌 검증의 몫이 아니다.
  → **직선 항로가 열린 해협만 몰아 보고**, 개선 여부는 "옛 마스크가 막던 바다가 열렸는가"
  로 따로 재는 쪽으로 바꿨다.
- 모서리 탈출 시험에서 처음 잡은 법선 방향을 30프레임 내내 고정했더니, 배가 해안을 따라
  7km 넘게 밀려간 뒤 그 방향이 더는 바다 쪽이 아니어서 334/386 이 나왔다.
  → 매 프레임 **지금의** 바깥 법선으로 조타하게 바꾸니 398/398.

## 부록 C — 이번에 유효했던 작업 방식

- **추측을 멈추고 재라.** 마스크 해상도가 원인이라는 심증은 처음부터 있었으나,
  실제로 재보니 지브롤터·다르다넬스는 마스크에서도 살아 있었다. 배율 100배라는
  사용자의 한마디가 있고서야 원인이 확정됐다. **모르는 값 하나는 반드시 물어본다.**
- **원본을 오려 검증한다.** `verify_coast.js` 는 `world_chart.html` 의 토막을 그대로
  vm 에서 돌린다. 재구현하면 시험과 코드가 갈라진다.
- **브루트포스 대조.** 색인 조회를 전수 조사 결과와 맞춰 본 것이 남극 색인 누락을 잡았다.
  최적화된 자료구조는 반드시 느린 참값과 대조한다.
- **시험이 틀렸을 가능성을 먼저 의심한다.** 이번 세 번의 실패 중 둘이 시험 쪽 문제였다.
  충돌 검증에 항로 탐색을 섞지 말 것.
- **불변식으로 설계한다.** "해안선에서 HULL_R 이상 떨어져 있다" 하나로 관통·안팎 판정·
  시계 배속 문제가 한꺼번에 사라졌다.

## 부록 D — 다음 단계 후보

**1. `HULL_KM` 과 배 그림의 비율** *(사용자 확인 대기)*
HUD 기준 배 1척이 5.6km 인데 실제로 막는 반지름은 0.2km — 그림의 1/28 이다. 물리적으로는
뱃머리 끝 한 점만 물에 있으면 통과라, 100배에서는 배가 육지에 얹혀 보인다. 배 그림 크기
(`P.shipScale`)에 연동하는 방법이 있으나 배율에 따라 물리가 달라지는 문제가 생긴다.
실제로 몰아 본 뒤 정한다.

**2. 100배에 걸맞은 해안선 자료**
선분 평균 15.74km — 100배에서 화면 322px 짜리 직선이다. 스크린샷의 각진 모서리가 이것이다.
`build_land.py` 를 ne_10m 으로 다시 돌려야 하는데 걸림돌이 있다. `land_data.js` 는 좌표를
Int16 × `scale=100` 으로 담아 0.01°(1.11km)에서 정밀도가 막힌다. 경도 180×scale 이
32,767 을 넘을 수 없으므로 scale 상한은 180, 즉 0.6km 가 한계다. **더 가려면 델타 부호화나
Int32 로 형식을 바꿔야 한다.** 파일 크기도 함께 검토할 것.

**3. 좌초를 사고답게**
지금은 `speed=0` 만 한다. 선체 손상·수리를 넣으면 좌초에 무게가 생긴다.
`moveWithCoast` 가 `out.hit` 을 이미 돌려주므로 접촉 세기를 재는 자리는 마련돼 있다.

**4. 묵은 검증 실패 여섯**
`verify_helm`, `verify_sail`, `verify_sailable`, `verify_ui`, `verify_windsail`,
`verify_zoom`. 이번 변경과 무관하며 지난 세션에서도 깨져 있었다. 원인은 원본에서 토막을
오려 내는 정규식이 코드 변화를 못 따라간 것(`<script>` 패턴, `SHIP` 미정의, `TUNE_W` 부재).
한 번에 손보면 좋다.

**5. 육지 발견(sight)도 선분으로?**
`updateSight` 주변의 육지 탐색은 아직 `isLand` 마스크를 쓴다. 20km 시야에서 3.46km 오차라
당장 급하지 않으나, 100배로 노시면 눈에 띌 수 있다.
